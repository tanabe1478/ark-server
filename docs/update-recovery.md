# 更新と復旧を通常運転から分離する

## 更新

ゲームのstartはdownload/updateを実行しません。`latest`を毎回取得したり、MODの開発版を自動適用しません。ゲームは固定バイナリ・MOD内容、runtimeはimage ID、Botは依存version/hashで管理します。

明示的な更新候補作成だけを、別コンテナで行えます。

```bash
python3 -m scripts.docker_update --image sha256:REVIEWED_RUNTIME_IMAGE_ID --confirm
```

既存の公式SteamCMDを新しい候補ディレクトリへコピーし、匿名のApp 376030更新をその候補にだけ適用します。Saved・認証・Bot token・Docker socketはコンテナへ渡しません。本番のファイルを上書きせず、起動・昇格も行いません。失敗／時間切れのjobを自動再実行しません。候補と失敗記録は保全します。

このコマンドはMOD更新・ワールド移入・ビルドの観測承認を行いません。候補のバイナリが未対応なら、アドレス流用や終了値許可で通してはいけません。

1. 現releaseのコマンドで本番を検証付き停止し、設定・Saved・MOD・image/profileを退避する。
2. 候補と別Savedコピーで起動／保存／再読込・MODを検証する。本番へコピーを書き戻さない。
3. バイナリ・観測コード・依存image・設定の差分をレビューし、新しい契約を明示承認する。
4. 切替の意図と復旧手順を保存してから配置する。未知の失敗は中止する。

稼働中のreleaseのソースを変更すると停止時のcontract検査も失効します。先に現releaseで停止するか、別checkoutで候補を作ってください。既存Docker runtimeの契約を`activate-game`で黙って上書きすることはできません。初回移行と、その後のバージョン更新は別レビューです。

## 復旧

「ゲームが止まった」「ファイルhashが一致した」「保存コマンドが応答した」は、完全なゲーム内整合性の証明ではありません。失敗時はまず現在のSavedと証拠を保全し、最後の検証済み停止と差分を確認します。

古い移行元のhashへ戻すために、新しいキャラクター・進捗を上書きしません。初期package、古いバックアップ、現在のSavedを別々に保管します。復元は停止確認・プレビュー・revision確認・所有者承認を経て行い、勝手に起動しません。

Docker volumeの永続化だけではバックアップになりません。同じSSDの退避だけではSSD故障にも対応できません。秘密を含むバックアップを別媒体へ権限を保ってコピーし、別データ領域で復元試験を行ってください。

旧`backup.sh`の正常停止0専用経路は、証拠付き停止policyの環境では停止前に拒否します。タイマーを安易に有効にせず、検証付き停止が行う全Saved退避を利用します。unknown/failedの記録削除、終了値の書換え、成功コード追加でバックアップや再起動を通しません。
